# segmented-append-log-go

一个可崩溃恢复的**分段式追加日志（segmented append-only log）**存储组件，
作为上层数据库 / 消息系统的本地持久化底座。仅依赖 Go 标准库，不依赖任何
外部服务、网络或凭据。

它保证：进程在写入中途异常终止、存在并发读写时，重启后仍能得到
**确定且可复现**的数据结论；读取方只看到完整、已提交、序号连续的记录。

---

## 1. 磁盘存储格式与版本兼容

### 1.1 分段文件

数据目录下每个分段是一个独立文件，文件名即其起始逻辑位置：

```
segment-00000000000000000000.log
segment-00000000000000000005.log
...
```

- 20 位零填充的 `basePosition`，字典序即位置升序；
- 每个分段由若干**帧（frame）**顺序拼接而成；
- 最后一个分段是“活动分段（active）”，仅它可写，其余分段只读且不可变；
- 一条记录的所有帧都落在同一分段内（见 §1.3 的滚动规则）。

### 1.2 帧格式（当前版本 `v1`，魔数 `"SL"`）

```
偏移   长度    字段        说明
0      2      magic      固定 0x53 0x4C（"SL"），用于识别帧/文件归属
2      1      version    帧格式版本，当前为 1（FormatVersionV1）
3      1      flags      分片标志位：bit0=first，bit1=last
4      8      seq        记录逻辑序号（uint64，大端），同记录所有帧共享
12     4      dataLen    本帧负载长度（uint32，大端）
16     4      dataCRC32  仅对本帧负载计算的 IEEE CRC-32（uint32，大端）
20     N      data       本帧负载
```

`flags` 取值：

| flags | 含义 |
|-------|------|
| `first|last` (0x3) | 单帧完整记录 |
| `first` (0x1) | 多帧记录的首帧 |
| `0` | 多帧记录的中间帧 |
| `last` (0x2) | 多帧记录的尾帧 |

### 1.3 记录拆分与分段滚动

- 超过 `MaxChunkBytes` 的记录会被拆成多帧（首帧 / 若干中间帧 / 尾帧），
  只有拿到尾帧才算一条完整记录；
- **滚动只发生在一条记录的首帧之前**：当活动分段放不下该记录的下一帧时，
  先把当前活动分段 `fsync` 并密封，再创建以该记录 `seq` 命名的新分段。
  因此中间帧永远不会成为新分段的第一帧，恢复时不会出现“有尾无头”的链。

### 1.4 版本与兼容规则

- 解析时**只接受** `version == 1` 且魔数为 `"SL"` 的帧；
- 遇到无法识别的魔数 / 版本，按 `invalid-magic` 损坏处理并在该处停止扫描
  （详见恢复语义），绝不会把未知字节误当成记录返回；
- 版本号写入每一帧头，未来可按帧升级。新版本组件对旧版本目录的兼容策略：
  旧帧按其原有规则解释（前向兼容在设计上预留）；旧版本组件遇到更高版本
  帧会得到明确的 `invalid-magic` 归类，而不是静默错乱。

## 2. 恢复语义（崩溃恢复）

打开目录时执行 `recoverDir`。恢复**只依据磁盘上的字节**，不写入也不依赖
任何“正常关闭”标记，所以**正常关闭与异常终止（kill -9 / 断电 / 不 fsync）
对同一份磁盘数据得到完全一致的可用范围**。

算法把所有分段视作一条连续字节流，运行帧状态机：

1. 列出全部合法分段文件，按 `basePosition` 排序；
2. 从流头顺序读帧，校验魔数、版本、CRC，并维护“首帧→中间帧→尾帧”的
   分片链状态与记录序号连续性；
3. **第一个**不满足条件的位置即损坏点：从损坏帧起到流末尾的全部字节一律
   视为尾部残余——
   - 损坏点之前的分段原样保留；
   - 损坏点所在分段截断到损坏偏移（可能清空）；
   - 损坏点之后的分段整段删除；
4. 截断 / 删除都配合 `fsync` 与目录 `fsync`，使修复结论本身持久化。

损坏归类（`RecoveryInfo.Corruption`，可在日志中打印）：

| 归类 | 触发情形 |
|------|----------|
| `none` | 所有帧都构成完整、校验正确、序号连续的记录 |
| `truncated-tail` | 帧头不足、负载被截断，或多帧记录缺少尾帧（写入中途崩溃的典型现场） |
| `checksum-mismatch` | 帧结构完整但负载 CRC-32 不符 |
| `invalid-magic` | 魔数 / 版本无法识别 |
| `sequence-gap` | 记录序号不连续（中间缺号或乱序） |

关键确定性保证：

- **单条记录是原子可见的**：全部帧写齐（并按配置 fsync）后才推进提交位置；
  半条记录在恢复时整条丢弃，永远不会被当作完整记录返回。
- **跨分段悬挂链回退**：若损坏的是一条跨段链的中间/尾帧，截断点回退到该链
  的首帧之前，绝不保留半条链。
- **可复现**：对同一份字节多次打开，结论逐字节一致（修复后第二次打开为
  `none`，提交位置不变）。

`RecoveryInfo` 同时给出 `FirstPosition`、`CommittedPosition`、被修复的
尾部文件 `TailPath`、保留 / 丢弃字节数 `KeptBytes`/`DroppedBytes`、全部
保留分段 `Segments` 以及人类可读 `Reason`。

## 3. 读取模型与并发

- **逻辑位置 = 记录序号（seq）**，从 0 起单调递增；`CommittedPosition()`
  返回下一条待写入记录的序号，也是已提交记录的排他上界。
- `NewReader(pos)` 创建**独立游标**，`pos` 必须位于
  `[FirstPosition(), CommittedPosition()]`：
  - `Next(ctx)` 阻塞等待下一条已提交记录；
  - `TryNext()` 非阻塞，无新记录时返回可区分的 `ErrNoRecord`；
  - 读取严格连续推进，不重复、不跳号。
- 多写者、多读者可并发使用，并通过 `-race` 验证：
  - 写入由单一追加互斥串行化，位置分配无重复无空洞；
  - 读取只读取“已提交字节边界”之内的数据，配合每分段 `RWMutex` 建立
    happens-before，绝不会读到写了一半的帧；
  - 读路径使用**独立的只读 fd**，写路径使用独立读写 fd（pwrite 显式偏移），
    读写 fd 互不共享 `*os.File`；
  - 只读 fd 由 LRU 句柄缓存按 `MaxOpenFiles` 有界换入换出，正在读取
    （被 pin）的分段不会被换出或删除。

### 资源上限与背压

达到上限时得到的是**可区分的拒绝结果**，而不是静默丢弃或阻塞整个进程：

- 单条记录超过 `MaxRecordBytes` → `ErrRecordTooLarge`；
- 分段数达 `MaxSegments`、或总字节达 `MaxTotalBytes`，且自动回收后仍
  腾不出空间 → `ErrStorageLimit`；
- 只读句柄额度被长期占用的读取方占满 → 读路径同样得到 `ErrStorageLimit`。

### 旧数据回收

`Reclaim()` 删除“被所有存活读取方越过”且“早于 `RetainBytes` 保留水位”
的旧分段（活动分段永不删除）：

- 安全边界取所有读取方下一条待读位置的最小值；仍被读取方需要的分段
  绝不回收（慢速消费者得到保护）；
- 正在被读取的分段本轮跳过，下一轮再回收；
- 回收后 `FirstPosition()` 前移，过旧的 `NewReader(pos)` 返回
  `ErrBadPosition`；写入序号继续连续，不受回收影响。

## 4. 可配置项（`Config`）

| 字段 | 默认 | 说明 |
|------|------|------|
| `MaxSegmentBytes` | 64 MiB | 单分段目标大小；超过后在下一记录首帧前滚动 |
| `MaxRecordBytes` | 0（不限） | 单条记录最大字节数，超限返回 `ErrRecordTooLarge` |
| `MaxSegments` | 0（不限） | 保留分段数量上限（含活动分段） |
| `MaxTotalBytes` | 0（不限） | 全部分段总字节数上限 |
| `MaxOpenFiles` | 16 | 同时打开的 fd 上限（含 1 个写 fd，其余为只读 fd） |
| `FsyncEveryWrite` | `false` | 每条记录 fsync；关闭时仅滚动 / Close 时 fsync（崩溃可能丢尾部，但恢复结论仍确定） |
| `RetainBytes` | 0（不额外保留） | 回收保留水位：早于 `totalBytes-RetainBytes` 的分段才可回收 |
| `MaxChunkBytes` | 约半个分段 | 单帧负载上限，超过则把记录拆成多帧 |

## 5. 错误归类速查（`errors.Is`）

| 错误 | 含义 |
|------|------|
| `ErrIncompleteRecord` | 尾部残余 / 帧或分片链不完整，不能作为完整记录 |
| `ErrChecksumMismatch` | 帧负载 CRC-32 校验失败 |
| `ErrInvalidMagic` | 帧魔数 / 版本无法识别 |
| `ErrSequenceGap` | 记录序号不连续 |
| `ErrRecordTooLarge` | 单条记录超过 `MaxRecordBytes` |
| `ErrStorageLimit` | 分段 / 字节 / 句柄达上限且无法回收（背压） |
| `ErrNoRecord` | 非阻塞读取时暂无已提交新记录 |
| `ErrBadPosition` | 读取位置非法或已被回收 |
| `ErrClosed` | 日志或读取器已关闭 |

## 6. 本地验证方法

仅需 Go 工具链（模块声明 `go 1.25`），无外部依赖：

```sh
# 编译与静态检查
go build ./...
go vet ./...

# 全部测试（普通模式）
go test ./...

# 并发安全：竞态检测
go test -race ./...

# 查看恢复位置与错误归类日志（测试会 t.Logf 打印）
go test -race -v ./...

# 只跑崩溃恢复 / 并发 / 回收相关用例
go test -race -v -run 'TestRecovery|TestCrash|TestAbrupt|TestConcurrent|TestSlow|TestReclaim|TestMax|TestBounded' ./...
```

测试覆盖：

- 不同写入阶段（写前 / fsync 前 / fsync 后）注入失败；
- 尾部帧头截断、负载截断、CRC 损坏、魔数损坏、序号跳号、多帧记录缺尾帧；
- 损坏出现在后随分段时的截断与删除；
- 正常关闭 vs 异常终止对同一字节序列的恢复结论一致性与可复现性；
- 多写者位置连续无重复、多读者各看到全部记录恰好一次（`-race`）；
- 慢速消费者保护、旧数据回收安全边界、分段 / 字节 / fd 上限背压。
